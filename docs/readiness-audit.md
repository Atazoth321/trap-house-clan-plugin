## Incomplete behavior and concrete findings

1. **Privileges are member-scoped, not token-scoped.** `RankingStore.authenticate` prefers member_permissions over a credential's legacy administrator flag. Every credential for the Owner identity gets Owner rights, even one created with `issue-token Name member`. Keeping a separate staff token does not make the same identity's plugin token low privilege. Scope support or a separately verified low-privilege identity would be needed for that separation. Local RuneLite configuration masks tokens but does not encrypt them.
2. **There is no singleton Owner constraint.** Backend operations check the OWNER role. Operator bootstrap can assign that role to multiple members. Ensure only the actual clan Owner has it; the API cannot delegate OWNER, but the operator can.
3. **Client observations are not independently attested game evidence.** A modified client or stolen member token can fabricate matching events or progress, subject to caps and deduplication. No Jagex verification API or anti-cheat proof is implemented. Membership and character ownership require independent staff verification.
4. **Coverage is not every OSRS activity/item.** Real item artwork support is not a scoring catalogue. No comprehensive reward policy is seeded; raid/event chests, universal boss kills, PvP/minigame coverage, historical loot import and complete historical collection/pet reconstruction are absent. Available bank containers do not provide a historical inventory. Only two pet-insurance probes are seeded.
5. **Observation delivery is not durable on the client.** Queue is memory-only, max 200 observations, up to 20 submissions per sync, approximately 30-second periodic sync. Overflow, logout, config/account change, shutdown or restart can discard unsubmitted observations. Rejected unconfigured/capped events are removed; enabling a rule later does not recover them.
6. **Owner/staff administration is API/database-only.** No owner dashboard or buttons for adjusting points, assigning/locking ranks, editing policy, issuing credentials or reviewing audit exist. Member reward requests are implemented; staff reviews use the API. Event managers can publish existing events, not create them through an event-creation API.
7. **Leaderboard label is inaccurate.** `RankingPanel.openFullBoard` labels its last column “Eligible rank” but fills it from `rank` (effective assigned/application rank), not `automaticRank`. Profiles do expose the separate values.
8. **Item-name search can miss displayed items.** PointsLog searches stored SQL titles before RuneLite resolves an ID to a name. With an empty rule.display_name, a loot key like `NPC:4151` will not match “Abyssal whip” even though that is rendered on the card. Configure rule display names or implement name-aware search.
9. **Adjustment reasons are shared profile information.** Other authenticated active members can read adjustment reasons through recent history and Misc logs. The staff audit is restricted, but that does not make these reasons private.
10. **Promotion notices are advisory.** Unassigned members are considered eligible for their automatic rank, even Recruit at zero points; initial deployment may queue baseline notices. Notices deduplicate by member/rank, not every threshold edit or recurring promotion. The service never updates actual OSRS ranks or observes whether leadership changed them in-game.
11. **Operational components are manual.** No tested deployment unit, container stack, scripted runtime grants, public TLS setup, backup/restore automation or full versioned migration system is supplied. `/health` is process-only, not database/outbox readiness. Database-owner access can disable triggers; permanent retention depends on operational controls/backups.
12. **Docs/dependencies need reconciliation before release.** Some docs still say brown/gold profile or top-50 leaderboard; current code uses the shared dark/red style and LIMIT 1000. RuneLite uses `latest.release`, so a later rebuild can use a different client version. Existing working-tree changes, including server code, are not all committed.

## Manual launch checklist

1. Preserve the current project in version control and back up any existing database. Review the many uncommitted/untracked changes. Choose a tested RuneLite version for repeatable releases. Do not store operational databases underneath a directory deleted by Gradle clean.
2. Choose an always-on host for the ranking service and PostgreSQL 16+ (same host or managed PostgreSQL). Keep PostgreSQL private. Prepare DNS for a dedicated API origin, such as `https://rankings.your-domain.example`; the plugin accepts an HTTPS origin with no path/query.
3. Install a supported JDK for Gradle (this audit used JDK 26; code targets Java 11) and deploy the existing backend source/resources with the wrapper. `runServer` is the provided launch path; the plugin JAR does not start or bundle the server/JDBC driver. Add an OS service/process supervisor for restart-on-failure and boot startup.
4. Create the production database, a schema-owner/migration role and a separate non-owner runtime role. Keep backup and operator credentials separate. Use a dedicated disposable test database for tests. Configure certificate-verified database TLS when connecting remotely.
5. Set TRAP_DATABASE_URL (`jdbc:postgresql://host:5432/traphouse`, with appropriate TLS parameters), TRAP_DATABASE_USER and TRAP_DATABASE_PASSWORD in the backend process environment/secret store. TRAP_PORT defaults to 8090. Use migration credentials to run `gradlew runServer --args=init`; back up before upgrading an existing database. Init applies schema.sql and 19 tracking-only starter goals; it does not configure live scoring or a roster.
6. Grant the runtime role the table/view/sequence permissions needed by the current code, including SELECT on rank aliases and retained-rank views, INSERT for ledger/events/history/audit/adjustments/notices/outbox, and the necessary state updates. Registration cancellation also needs DELETE on event_registrations. Verify least-privilege operation through the full integration and staging flows. Do not grant history UPDATE/DELETE/TRUNCATE or schema/trigger modification rights; never run the service as the schema owner/superuser.
7. Independently verify clan membership and character ownership. Insert members with stable UUIDs and normalized lowercase names, for example:

   ```sql
   INSERT INTO members(id,name,normalized_name)
   VALUES (gen_random_uuid(),'Example','example');
   SELECT id,name FROM members WHERE active;
   ```

   Preserve UUIDs through verified renames. Deactivate departed members and revoke their credentials.
8. Using the actual verified Owner UUID, run `gradlew runServer --args="bootstrap-owner <owner-uuid>"`. Verify only that identity has OWNER permission. Assign the displayed Owner/staff rank separately through the rank API; displayed titles never grant API authority. Set other staff roles through the Owner-only permission endpoint.
9. Issue individual credentials with `gradlew runServer --args="issue-token Example member"` (quote the complete args string, and quote a character name containing spaces within it). Deliver the generated token privately and plan renewal before its 90-day expiry. Use privileged credentials only with the member-scoped caveat above. There is no official OSRS/Jagex API key, owner password login, or MFA setup in this project.
10. Decide real thresholds/rewards/caps/categories. Configure ranks, rules and goals through trusted SQL tooling. LOOT keys must be exact `npcId:itemId`; COMBAT/COLLECTION keys must match normalized supported messages. Set categories and human-readable display_name values. Enable only agreed rules. Assign positive points to chosen starter goals only after reviewing their probe semantics and current game IDs. Optional clan events/races/manual reward rules also require definitions. Registration and race placement do not automatically pay rewards.
11. Configure a trusted HTTPS reverse proxy forwarding to 127.0.0.1:8090, with a valid certificate, body/header/time/connection limits and IP rate limiting. Keep the raw listener and database off the public network. Start `gradlew runServer` using runtime database credentials. Check `/health`, then an authenticated dashboard request; process health alone does not validate the database schema.
12. Create a Discord incoming webhook in the desired leadership channel and set TRAP_DISCORD_WEBHOOK in the backend only; restart the service. No Discord bot token/application key is used by this implementation. Awards and promotion notices share that webhook. Verify real receipt in a test channel, retry behavior and outbox delivery markers before using the leadership channel. Expect possible duplicate notifications, not duplicate points, on transport retries.
13. WOM public competition reads require no API key in this code. Maintain group 2504 competitions, with valid participant baselines and updated WOM profiles. Set competition IDs in plugin settings if using overrides. Set TRAP_WOM_STATS_ENABLED=true only if you want optional EHP/EHB imports and accept sending roster names to WOM; test a profile import separately.
14. Configure the disposable integration database and run the suite:

   ```powershell
   $env:TRAP_TEST_DATABASE_URL='jdbc:postgresql://127.0.0.1:5432/traphouse_test'
   $env:TRAP_TEST_DATABASE_USER='<test-role>'
   $env:TRAP_TEST_DATABASE_PASSWORD='<test-password>'
   .\gradlew.bat serverIntegrationTest
   ```

   Tests create and drop random schemas and require matching database permissions. Do not point them at the production database. Passing these tests was not achieved in this audit.
15. Run a staging pilot through the real HTTPS API and a logged-in RuneLite client: verify one configured award, retry deduplication, cap enforcement, source breakdown, leaderboard/member profile and actual item sprite. Verify Administrator/Event Manager/Member deduction HTTP requests get 403, Owner correction records the complete audit, overdrafts fail, earned rank survives deductions, protected-rank changes require Owner, and revocation rejects the next request. Verify restart persistence and a database restore. Do not call the system production-ready until these pass.
16. Distribute the actual plugin through a supported installation/development process or submit it for Plugin Hub review. Building a JAR, the Swing sample window, or the HTML/ZIP preview does not install the plugin into another person's normal RuneLite. Each real member must enable ranking sync, enter the HTTPS origin and their own token, be in the actual TRAP HOUSE clan and verified server roster, and enable the relevant system notifications. Restart the development client after code updates.
17. Monitor service/database availability, request errors/rate limits, outbox backlog/retry attempts, backups, certificate and token expiry. Review scoring disputes and suspicious activity; perform actual OSRS promotions/demotions manually. Keep the permanent ledger and audit backups with a tested restore procedure.
